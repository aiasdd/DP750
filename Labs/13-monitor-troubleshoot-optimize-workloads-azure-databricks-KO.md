# 랩 13: Azure Databricks에서 워크로드 모니터링, 문제 해결 및 최적화

## 소개

예전에는 몇 초 안에 완료되던 쿼리가 이제는 몇 분이 걸립니다. 클러스터 리소스가 바쁜 것 같지만 대부분의 작업은 거의 즉시 완료되는 반면 소수의 작업이 끌립니다. 이것이 **데이터 스큐**의 특징입니다 — 그리고 종종 **과도한 셔플**이 동반되어 Spark이 단계 간의 네트워크 전체에서 큰 양의 데이터를 이동하도록 합니다.

이 랩에서는 두 문제를 의도적으로 재현하여 Spark UI에서 정확히 어떻게 보이는지 관찰한 다음 대상 지정 수정을 적용하고 개선을 확인할 수 있습니다.

| 부분 | 주제 | 위치 |
|------|-------|--------|
| **파트 1** | 환경 설정 및 데이터 생성 | 노트북 |
| **파트 2** | 데이터 스큐 노출 및 Spark UI 검사 | 노트북 + 랩 지침 |
| **파트 3** | 데이터 스큐 수정 | 노트북 |
| **파트 4** | 과도한 셔플 노출 및 Spark UI 검사 | 노트북 + 랩 지침 |
| **파트 5** | 셔플 오버헤드 감소 | 노트북 |

## 컴퓨팅 클러스터 생성

이 랩에는 **클래식 컴퓨팅 클러스터**가 필요합니다(서버리스 아님). 적응형 쿼리 실행을 비활성화하고 다시 활성화하는 데 사용되는 일부 Spark 구성 옵션(예: *spark.databricks.optimizer.adaptive.enabled*)은 클래식 클러스터에서만 사용할 수 있습니다.

> ⚠️ **Photon을 비활성화해야 합니다.** Photon은 Databricks의 벡터화된 쿼리 엔진입니다. 활성화되면 셔플 및 스큐 처리를 자동으로 최적화하여 이 랩이 시연하도록 설계된 성능 문제를 숨깁니다. Photon이 활성화되어 있으면 Spark UI에서 스큐된 작업 분포나 높은 셔플 메트릭을 볼 수 없습니다.

1. Databricks 작업 영역에서 왼쪽 사이드바의 **컴퓨팅**을 클릭합니다.
2. **컴퓨팅 생성**을 클릭합니다.
3. 다음 최소 설정으로 클러스터를 구성합니다:

   | 설정 | 값 |
   |---------|-------|
   | **클러스터 이름** | `perf-lab` |
   | **정책** | 제한 없음 |
   | **단일 노드** | 활성화 |
   | **액세스 모드** | 단일 사용자 |
   | **Databricks Runtime** | 최신 LTS(ML 아님) — **Photon이 아닌 런타임을 선택해야 합니다** |
   | **노드 유형** | 가능한 가장 작은 것을 선택합니다(예: `Standard_DS3_v2` 또는 동등한 것) |
   | **자동 종료** | 30분 |

4. **고급 옵션**을 확장한 다음 **Spark** 탭을 클릭합니다. **Spark 구성** 상자에 다음 줄을 추가하여 Photon을 명시적으로 비활성화합니다:

   ```
   spark.databricks.photon.enabled false
   ```

5. **컴퓨팅 생성**을 클릭하고 클러스터가 **실행 중** 상태에 도달할 때까지 기다립니다.

## 파트 2: Spark UI에서 데이터 스큐 조사

노트북의 **연습 2**에 있는 셀을 실행한 후 여기로 돌아와 아래 단계를 따라 Spark UI에서 스큐된 실행을 검사합니다.

### Spark UI 열기

1. Databricks 작업 영역에서 왼쪽 사이드바의 **컴퓨팅**을 클릭한 다음 **perf-lab** 클러스터를 클릭합니다. 클러스터 세부 정보 페이지에서 **Spark UI** 탭을 클릭합니다. Spark UI가 새 브라우저 탭에서 열립니다.
2. **작업** 페이지에 도착하며, 이 세션 중에 트리거된 모든 Spark 작업이 나열됩니다.

### 스큐된 집계 작업 식별

3. 가장 최근에 완료된 작업을 찾습니다. **작업 2.1**의 **groupBy 집계** 및 **작업 2.2**의 **정렬-병합 조인**이 맨 위(최신순)에 나타날 것입니다.
4. 집계 작업을 클릭합니다(*aggregate* 또는 *hashAggregate*와 관련된 단계를 참조할 것입니다).
5. 작업 세부 정보 페이지의 **단계** 목록을 살펴봅니다. 셔플을 수행한 단계를 클릭합니다 — 일반적으로 가장 많은 작업과 가장 긴 기간을 가진 것입니다.
6. 해당 단계의 작업에 대한 **요약 메트릭** 표로 스크롤합니다. **기간** 행에 집중합니다:
   - **최소**, **25번째 백분위수**, **중앙값**, **75번째 백분위수** 및 **최대** 값을 기록합니다.
   - **최대**가 **75번째 백분위수**보다 50% 이상 높으면 데이터 스큐를 보고 있습니다 — 소수의 작업이 대부분의 데이터를 처리합니다.
7. 더 가까이 스크롤하여 **작업** 섹션을 봅니다. 목록을 **기간**(내림차순)으로 정렬합니다. 하나 또는 두 개의 작업이 나머지보다 훨씬 더 긴 기간을 가진 것을 관찰합니다.

### 스큐된 조인 작업 식별

8. Spark UI 왼쪽 탐색에서 **작업**을 클릭하여 작업 목록으로 돌아갑니다.
9. 작업 2.2의 정렬-병합 조인 작업을 클릭하고 분석을 반복합니다. 동일한 패턴을 찾습니다: 대다수보다 훨씬 더 긴 기간의 몇 가지 작업.
10. 조사를 완료했으면 노트북으로 돌아가 **연습 3**을 계속합니다.

## 파트 4: Spark UI에서 과도한 셔플 조사

노트북의 **연습 4**에 있는 셀을 실행한 후 여기로 돌아와 셔플 메트릭을 조사합니다.

### 셔플이 많은 단계 찾기

1. Spark UI 탭으로 돌아갑니다(또는 노트북 도구 모음에서 다시 엽니다).
2. 왼쪽 탐색에서 **단계** 탭을 클릭하여 모든 작업에 걸쳐 모든 단계를 봅니다.
3. **셔플 읽음** 및 **셔플 쓰기** 열을 살펴봅니다. 연습 4에 의해 트리거된 단계는 두 열에 모두 상당한 데이터 이동을 보여 줍니다 — 많은 경우 실제 입력 데이터 크기보다 훨씬 더 많습니다.

### DAG에서 Exchange 노드 개수

4. 높은 셔플 값이 있는 단계를 클릭하여 세부 정보 페이지를 엽니다.
5. 단계 세부 정보 페이지의 위쪽에서 **DAG 시각화**를 확장합니다. **Exchange**라는 레이블이 지정된 노드를 찾습니다 — 각 노드는 클러스터 네트워크 전체에서 데이터의 전체 셔플을 나타냅니다.
6. 연습 4 작업의 단계 전체에서 표시되는 총 Exchange 노드 수를 개수합니다. 이를 groupBy → 조인 → 정렬 파이프라인에 실제로 필요한 최소 셔플 수와 비교합니다.

### 셔플 읽음 대 입력 크기 비교

7. 여전히 단계 세부 정보 페이지에서 **요약 메트릭** 섹션으로 스크롤합니다. **입력 크기 / 기록**과 **셔플 읽음 크기 / 기록**을 비교합니다. 셔플 읽음이 원본 입력보다 훨씬 크면 파이프라인은 필요한 것보다 더 많은 네트워크 I/O를 수행합니다.
8. 조사를 완료했으면 노트북으로 돌아가 **연습 5**를 계속합니다.
